## Integration decisions

The fork and upstream both used schema version 8 for different changes.
The fork's existing versions 8–11 keep their meaning. Before adding the
ownership column, migration 8→9 ensures package tables exist, allowing an
upstream v8 database (which has no package tables) to upgrade. Migration
11→12 performs upstream's orphaned `project_default_export_agents` cleanup.
Existing package bindings, artifact keys and ownership metadata are preserved.

Package import continues to call the unscoped `clone_repo_ref` entry point.
In v1.38.0 this delegates to `clone_repo_ref_scoped` with no subpath, so the
scanner still receives the full repository, including sibling plugin artifacts.
Single-skill installs retain upstream's sparse checkout optimization.

The native Claude upgrade, Codex generated marketplace/adoption, hook ownership
and project manifest behavior remain covered by the existing package tests.

## Upstream proposal and trade-offs

This is an additive package layer, not a replacement for presets. A package
tracks a Git source/revision and its artifacts; a binding records how one
artifact is applied to a tool and scope. A preset remains a working selection
of skills. Installing a package does not implicitly activate a preset, and
switching presets must not uninstall global plugins.

Provider-native plugin installation stays delegated to the provider CLI.
Portable skills use existing deployment primitives. Compatibility is selected
from discovered manifests and supported surfaces, rather than a new adapter
for each repository. A Claude manifest alone is not proof of Codex compatibility;
unsupported surfaces are refused instead of being silently converted.

Ownership is explicit: adopted external installations must not be uninstalled
as manager-owned resources. Installation plans show commands and risks before
approval. Rollback removes only newly created managed paths, not pre-existing
user directories or links. Manifest discovery is not a security audit: plugins
can contain executable hooks, MCP servers and setup commands.

Known boundaries for review:

- Claude supports native upgrade; the tested Codex CLI has no `plugin update`
  subcommand. Codex replacement is not presented as an atomic native upgrade.
- Codex native bindings are user-scoped; nested Codex hooks remain unsupported.
- Database schema 12 is not backwards-compatible with stock v1.38.0. Upstream
  maintainers should allocate the final migration number for their merge base;
  the fork's 8–11 migration history must not be copied blindly onto a newer base.
- Migration tests cover fresh databases, upstream v8 and fork state preservation.
  Application downgrade requires a pre-upgrade database backup.
- Native CLI smoke coverage does not establish cross-platform desktop E2E
  coverage. Windows provider behavior and real third-party hooks need separate UAT.

The proposed PR should be a draft for architecture/migration review first.
Maintainer acceptance of the package model cannot be established by local tests.

## Reproducible native CLI smoke test

Passed on 2026-09-08 in Linux Docker with Claude Code 2.1.259 and Codex 0.153.4:
Claude install 1.0.0 → native update 1.1.0 → uninstall; Codex install 1.1.0 →
remove (including installed cache) → install 1.2.0 → remove. Both test marketplace
registrations were removed, and the disposable container was automatically removed.

Run from the repository root. Only the test script is mounted, read-only; no
host home, provider config, package cache or Docker socket is mounted. Provider
state lives in the disposable container's default home. The fixture has no
hooks or MCP servers and does not require a model/API login. Registry downloads
require network access; these tools are not added as project dependencies.

```sh
docker run --rm --name qskills-native-smoke \
  --mount "type=bind,src=$(pwd)/scripts/native-plugin-smoke.mjs,dst=/smoke.mjs,readonly" \
  node:22-bookworm-slim sh -lc '
    apt-get update -qq &&
    apt-get install -y -qq git ca-certificates >/dev/null &&
    npm install -g @openai/codex@0.153.4 @anthropic-ai/claude-code@2.1.259 --no-audit --no-fund &&
    node /smoke.mjs
  '
```

The script asserts installed versions, absence after removal, and Codex cache
cleanup. Claude uses marketplace refresh followed by native `plugin update`.
Codex uses a local generated-format marketplace without a Git repository;
replacement is explicit remove/add, not an invented native upgrade command.

This smoke test validates provider command contracts only. Database ownership,
adoption, rollback and migration are tested separately in Rust; no real desktop
E2E or execution of third-party plugin hooks is claimed.

## Live Claude agent verification (2026-09-08)

The opt-in live tests use the authenticated macOS Claude Code CLI and Sonnet. They exercise
the actual package backend (`scan_package`, inventory persistence,
`create_binding`, `preview_binding`, `apply_binding`, `remove_binding`) with a
unique native plugins in **user (global)** and **project_local** scopes. No command doubles
or `--plugin-dir` injection are used. Other plugins and hooks are disabled only
for each test agent invocation; MCP is restricted and only the `Skill`
tool is exposed. Each invocation has a 120-second timeout and $1 budget cap.

Observed evidence:

- Install: Claude's initialization advertises `qskills-live-4ba30472c901:probe`
  from plugin version 1.0.0. An actual `Skill` tool call returns the unique
  receipt from that version's SKILL.md.
- Upgrade: the backend plans and executes `update_plugin`, persists managed
  ownership and the new applied revision. A fresh agent loads version 1.1.0,
  calls the same skill and returns a different unique receipt.
- Removal: the backend removes the binding/plugin. A fresh agent advertises
  no test plugin or test skill and replies: "Unavailable — no receipt to return."
- Both successful calls have no permission denials. Existing installed-plugin
  records are compared before and after and remain unchanged.

**Finding resolved: manager-added Claude marketplace registrations were left behind.**
The strengthened live test reproduced the bug (exit 101). Previously ownership
was recorded only for materialized Codex marketplaces. Now a read-only Claude
marketplace inventory precedes installation: an already registered marketplace
is not claimed, while a successful new registration is persisted as owned.
Malformed/failed inventory reads stop the operation rather than guessing ownership.

Removal transfers ownership to another matching managed binding, searching all
packages. Before unregistering a Claude marketplace it also checks the provider's
remaining installed plugins. This is necessary: a second failing live test proved
that Claude marketplace removal can uninstall other plugins in that marketplace.
Externally installed plugins therefore keep their marketplace registration.

Final explicit run: **4 live tests passed**, covering global and project-local
install/use/upgrade/remove, pre-existing marketplace preservation, and preservation
when another plugin still uses the marketplace. Normal tests: **512 passed**.
All fixture registrations/plugins were cleaned up. A final read-only check found
no `qskills-live-` entries in `installed_plugins.json`, `known_marketplaces.json`
or user `settings.json`. Existing installed-plugin records remained unchanged.

Legacy registrations without ownership evidence are not retroactively claimed
or deleted. If an external plugin keeps a marketplace alive, that registration
is deliberately retained rather than scheduling a later destructive cleanup.

Final simplification review fixes:

- Provider inventory JSON is parsed from raw successful stdout, without log
  sanitization/truncation or stderr concatenation. A regression test first failed
  with a 20 KB inventory plus a warning, then passed with the dedicated parser.
  Malformed JSON and unsuccessful process results are rejected.
- All lifecycle assertions are enclosed in one failure boundary. A common cleanup
  path attempts each test-owned removal before rethrowing an assertion failure.
  A temporary injected failure after installing both fixture plugins verified
  this path; no test entries remained afterward. The injected failure was removed.
- Only global/project-local skill-use tests call the model (six calls total).
  Pre-existing/shared-marketplace tests use native CLI and state assertions only.

The random receipts are not included in the agent prompt. The model cannot
pass by repeating an expected answer provided by the test. Plans and JSONL
transcripts are retained in the temporary evidence directory printed by the test.

```sh
QSKILLS_LIVE_CLAUDE=1 cargo test --manifest-path src-tauri/Cargo.toml --lib \
  core::package_manager::live_tests:: \
  -- --ignored --nocapture --test-threads=1
```

Remaining boundaries: this proves **backend → native installation → actual
Claude skill use**, not desktop button clicks or Git import/update fetching.
It seeds a local package inventory and revisions directly. It does not prove
Codex agent execution, Windows behavior, or
third-party hooks/MCP functionality. The earlier Docker test covers user-scope
CLI installation separately. Do not generalize this result to every plugin.

## Running

Run `npm run tauri:dev` to test the integrated desktop app. Opening an existing
library upgrades its database to schema 12. Older fork binaries and stock
upstream v1.38.0 do not support that schema; use a pre-upgrade database backup
if reverting the application. The Git backup branch preserves source code,
not the user's runtime database.
